# 代码整合与商业化审计

审计日期：2026 年 7 月 15 日

## 结论

当前系统已经具备预测、数据管理、可靠上报和离线部署的主体结构。本分支补齐了 SCADA 实发功率的采集审计、质量拒绝、幂等入库、数据新鲜度、故障恢复和前端运行状态。开发环境的五个场站已通过实时链路与无效质量码演练。

代码库仍有几类会影响正式场站运行的结构性问题。最高优先级集中在数据库迁移、进程职责、安全边界、完整数据契约和离线供应链。界面层冗余可以稍后处理，先保证数据链路可追溯和部署行为确定。

## 本分支已经收敛的事项

1. SCADA Worker 通过统一接入接口提交样本，后端在一个事务中保存来源审计和实际功率。
2. 无效质量码、异常功率、时钟偏差和过期数据会被拒绝并留下原因。
3. 同一场站、同一十五分钟的数据执行创建、更新或幂等去重。
4. 连接启动和停止改为数据库期望状态，由管理器统一收敛实际 Worker。
5. 前端展示 Worker、数据年龄、最近实际功率、预测消费状态和上报状态。
6. 研发用 HTTP 随机功率模式默认禁止创建和启动。
7. 数据库结构已纳入 Alembic 版本管理，应用启动不再自动补建业务表。
8. 旧训练链路、研发物理仿真和一次性数据库脚本已经退役。
9. SCADA 审计记录进入数据保留和归档流程。

## P0，场站试运行前完成

### 1. 持续执行正式数据库迁移基线

现状证据：

1. 仓库已经具备 `alembic.ini`、版本目录和统一管理命令。
2. 应用启动执行版本检查，不再调用 `Base.metadata.create_all` 补建业务表。
3. `20260715_02` 迁移通过数据存在性检查保护旧表退役。

风险：现场若跳过备份、升级演练或结构检查，仍可能因历史库差异中断发布。

建议：新增变更只能通过版本化脚本进入。发布流程持续执行备份、迁移预检、升级、结构校验和应用启动。

### 2. 将 SCADA 管理器拆成独立服务

现状证据：Flask 应用导入期间启动 SCADA 管理器，生产入口使用 Gunicorn 三个 Worker 和 `--preload`。当前分支通过数据库期望状态降低了多进程控制冲突。

风险：主进程预加载、线程和子进程派生顺序仍较复杂，重启和扩容时难以保证只有一个管理者。

建议：增加独立 `scada-manager` 容器。Web API 只写连接期望状态，管理器独占 Worker 生命周期和重启策略，并提供存活与就绪探针。

### 3. 收紧接口鉴权与网络访问范围

现状证据：SCADA 连接管理接口没有统一的角色权限装饰器，Worker 密钥在开发配置中允许为空。连接测试接口可以尝试访问大多数目标地址。数据库迁移脚本中还存在硬编码账号和密码。

风险：普通网络访问者可能修改采集配置、停止连接或利用连接测试访问内网服务。静态凭据也难以轮换和审计。

建议：管理接口要求管理员或运维角色，Worker 密钥在非开发模式下强制非空，连接目标应用场站网段白名单。移除脚本内静态凭据，全部密钥由离线发布配置注入。

### 4. 补齐 SCADA 与 NWP 的完整输入契约

现状证据：仿真测试床每个场站提供实发功率、风速、理论功率、可用功率和风机可用率五类点位。当前业务入库闭环只消费实发功率 IOA。NWP 接口仍处于待配置状态。

风险：依赖气象和运行状态的算法仍会使用历史数据、人工文件或空数据，页面显示与模型真实输入可能不一致。

建议：建立版本化点表映射，将五类 SCADA 指标统一归一化并落库。NWP 采用同一套来源编号、质量状态、时钟语义和隔离规则。每次预测保存输入数据版本和缺失率。

### 5. 固化离线构建供应链

现状证据：后端 Dockerfile 在构建时使用外部 APT 和 Python 软件源。仓库已有离线镜像与发布文档，但依赖锁定、软件物料清单和内部制品来源还没有完全统一。

风险：场站无法联网重建镜像，后续版本也可能因上游包变化产生不可重复结果。

建议：维护带哈希的 Python 锁定文件、离线 wheelhouse、基础镜像摘要和软件物料清单。发布包只引用已验收的内部制品，现场执行摘要校验后加载。

## P1，试运行稳定后收敛

### 1. 统一 API 命名空间

当前同时存在 `/scada/*`、`/api/*` 和 `/api/v1/*`。`v1_compat.py` 直接导入大量旧处理函数，模块体积大且耦合紧。建议冻结旧接口，所有新调用迁移到版本化蓝图，记录废弃日期和兼容测试。

### 2. 移除 ORM 兼容层依赖

静态扫描发现 17 个非测试 Python 文件仍导入旧 `models.py`。测试也会出现兼容层和 SQLAlchemy 旧接口警告。建议按业务域分批改为 `db_models`，每批补查询与事务测试，最后删除兼容导出。

### 3. 合并重复启动入口

仓库同时存在生产覆盖入口和旧 `backend/docker-entrypoint.sh`。旧入口包含乱码注释，完整 Compose 仍可能使用它。部署入口还会在运行时生成 Python 文件和修改源码注解。

建议：镜像构建阶段生成 WSGI 入口，容器启动只执行数据库预检和服务命令。管理员初始化改为一次性、显式且需要外部提供初始密钥的操作。

### 4. 拆分应用导入副作用

天气调度器、数据库检查和部分建表动作在模块导入期间运行。建议将 Web、预测调度、天气调度、SCADA 管理和维护任务拆成明确进程，每个进程只有一个入口和一个职责。

### 5. 控制仓库体积和运行产物

当前 Git 仍跟踪约 30,824 个 `frontend/node_modules` 文件、58 个模型产物、上传样例和 Celery Beat 状态文件。`.gitignore` 无法自动移除已跟踪文件。

这些内容承担了一部分离线开发能力，清理前需要先建立 wheel、npm 缓存和模型制品仓库。完成替代方案后，再在单独分支移出运行产物，避免影响当前生产发布。

### 6. 建立统一质量门禁

前端 `package.json` 没有 `lint` 命令和 ESLint 依赖，生产构建还报告大包体警告。Python 测试分散在正式测试目录和根目录脚本。

建议：固定一条后端测试命令、一条前端检查命令和一条完整验收命令。提交门禁至少覆盖单元测试、接口契约、前端构建、Compose 展开、Shell 语法和 SCADA 故障测试。

## P2，产品功能整理

1. `ExtremeWeatherCard.vue` 与 `extremeWeatherApi.js` 当前未进入主业务页面。
2. `backend/backend/utils` 属于运行入口补目录留下的嵌套结构。
3. 部分上传样例缺少所有者与保留说明。
4. SCADA 健康查询对每个场站执行多次查询，五场站影响较小，规模扩大前应改成批量查询。

建议为每个功能标注产品所有者、真实数据源、验收标准和删除日期。保留功能进入正式路线图，退出功能在独立清理提交中移除。

## 推荐实施顺序

1. 当前分支完成 SCADA 实发功率闭环和真实性展示。
2. 建立数据库迁移基线、接口鉴权和独立 SCADA 管理服务。
3. 完成五类 SCADA 指标与 NWP 的统一输入契约。
4. 在场站等价网络连续运行七天，验证时钟、断线、积压、预测时限和上报回执。
5. 固化离线制品供应链和回滚流程。
6. 最后处理兼容层、孤立页面、已跟踪依赖和仓库体积。

## 当前验收基线

当前分支应持续满足以下条件：

1. 五个测试场站均能通过 C104 产生新鲜数据。
2. 无效质量码进入审计表且不会覆盖最后有效实际功率。
3. 恢复正常场景后健康状态自动恢复。
4. 同一十五分钟重复样本不会产生重复实际功率记录。
5. 前端不把未知、缺失或接口异常显示为正常。
6. Windows 批处理脚本保持 CRLF，并通过 `cmd.exe` 实际执行验证。
