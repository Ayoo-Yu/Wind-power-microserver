# 气象数据拉取模块现状

## 当前定位

气象数据拉取模块负责管理场站气象服务器连接，按计划拉取文件，并记录文件级处理结果。预测所需的统一 NWP 入库仍由跨区接入处理器和 E 文本管道负责。

## 运行架构

```text
Web API
  负责连接与任务配置
        │
        ▼
KingBase weather_tasks
        │
        ▼
Celery Beat 动态加载计划
        │
        ▼
Celery Worker 执行 SSH 拉取
        │
        ├── weather_logs
        └── weather_data_records
```

核心实现位置：

1. `backend/routes/weather_fetch_router.py` 提供管理接口。
2. `backend/celery_app/scheduler.py` 从数据库动态加载五段式 cron 计划。
3. `backend/celery_app/tasks.py` 在独立 Worker 中执行任务，并通过 Redis 锁阻止同一任务并发运行。
4. `backend/services/task_executor.py` 完成文件拉取、本地处理和日志记录。
5. `backend/db_models/weather_fetch.py` 定义连接、任务、日志和文件处理记录。

## 生命周期约束

Web 进程导入应用时不会启动周期调度器。任务新增、更新、启停或删除后，Celery Beat 会在 `CELERY_BEAT_RELOAD_INTERVAL_SEC` 指定的时间内重新加载数据库配置。生产和本地开发均需要同时运行 Celery Worker 与 Celery Beat。

手动执行接口只负责提交队列，成功时返回 HTTP 202。页面随后通过任务日志查看真实结果。调度服务由进程管理工具维护，Web 接口不会直接重启 Celery Beat。

## 已实现能力

1. SFTP 和 SSH 密码或密钥连接配置。
2. 凭据加密存储与权限校验。
3. 五段式 cron 校验和动态加载。
4. 任务启停、软删除、手动入队和执行日志。
5. 文件级去重、本地处理记录与场站身份保留。
6. Redis 分布式锁与有限次数重试。

## 当前边界

1. 调度状态接口展示配置托管状态，不代表 Celery Beat 的实时进程心跳。服务存活情况应通过容器或 systemd 监控确认。
2. 拉取任务保存文件并记录处理元数据。预测特征表的统一入库由接入处理器或 E 文本管道完成。
3. 生产目录必须通过 Compose 持久化挂载，并在部署前确认 Worker 对目标目录具有写权限。
4. 数据到达率和解析质量仍需要基于真实批次记录完善，页面中的估算型指标需要继续清理。

## 运维检查

```bash
docker compose -f deploy/docker-compose.prod.yaml ps
docker compose -f deploy/docker-compose.prod.yaml logs --tail 200 celery-beat
docker compose -f deploy/docker-compose.prod.yaml logs --tail 200 celery-worker
```

任务未执行时依次检查 Celery Beat、Worker、Redis、cron 表达式、连接可达性和任务日志。
